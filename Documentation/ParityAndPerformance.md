# APK 4.6.0 对齐与性能改动（2026-10-28）

本轮以用户提供的安装包导出数据、IL2CPP 方法体和原预制体为依据。保留当前中文、纸质玩具美术、初始 500000 金币和全部主线关卡可选。源分析文件保存在项目外的 `D:/MiniProject/analysis/LoopSort0-parity-20261028/native/`。

## 玩法与关卡

- 主线 1299 条记录、每日挑战 30 条记录已重新导入。450/972 的 `block:G` 在原 `ParseColors` 中因枚举解析失败而被忽略，现按同一行为处理，不虚构玻璃机制。
- 每日挑战的长车支持 5–12 组容量和可选指定颜色；使用原长车部件、轮子、碰撞尺寸与伸缩绑定。货位、描边、填装和补车使用实际容量。
- 碎块密度使用已经采样的原样条长度，按原候选网格选择，单组深度乘数为 2。传送带按仍有碎块在外的整组占用槽位，不因收走一部分就提前腾出一组容量。
- 补入原空带/首关/最后货车的速度分支、失败原因与检查时序、冰块解锁时序。原 `BlockLoop` 是重复从相同货车放出的计数，不是每帧靠近或绕轨道的圈数。
- 打乱以连续同色及粘连关系组成的单位进行错位排列；撤回同时保存新规则状态。碎块继续保留组归属，只有靠近所属货车才进入。
- 生成器的接收上限为一组、普通完成阈值仍为四组，这是原 `TunnelCarrier.ProcessFeature` 与 `Carrier.GetCompleteBlockCount` 的真实行为；它作为供货容器发空即可，不将它改成普通四组接收车。

原远端 Lose/Pace 开关和服务端会话时限无法由 APK 静态数据确定，当前采用已核实的构造默认值，并在 Lua 中显式保留配置入口；不能将这些默认值说成已获取原线上 A/B 配置。

## 动画与资源

补入车辆驶入/刹停、车门变形、轨道逐段展开、箭头与传送门入场、钥匙飞行和开锁、卷门、冰块、地毯收卷、螺丝原动画剪辑、隐藏方块消融，以及原完成/破冰/隐藏揭示/入场粒子。

`import_animations.py` 保留原网格 377/393/395/413/427 的变形数据和剪辑曲线；`import_particles.py` 保留原粒子模块、网格与贴图；`import_long_carrier.py` 导入长车并补齐普通车原先遗漏的两扇门。原始图像没有经重新绘制。粒子 shader 是适配当前 Unity 版本及渲染管线的实现，不能承诺与原包逐像素一致。

## 帧率相关改动

- 可见碎块按网格批量提交 GPU 实例绘制；颜色随实例提交，消融材质继续独立绘制。不支持实例化的设备保留普通 Renderer 路径。
- 将每个碎块独立的出入协程合并为一个复用的飞行列表，保留原曲线、时长、暂停、epoch/version 中断与撤回行为。
- 刚体和碰撞体延迟到碎块第一次真正进入传送带时创建，静止的整块货物不预先创建物理组件。
- 继续使用当前已恢复的 BlockPhysics 物理路径，保留碰撞手感；接收动画阻挡按货车缓存，已有归属的碎块仅检查对应货车。
- 槽位计数缓存、HUD 状态缓存及每秒合并活动存档，减少重复计算、跨 Lua 调用和同步磁盘写入。
- 死局检查复用传送带颜色总数缓存，只扫描仍可接收货车中的货物，跳过已完成车及整条传送带的逐碎块访问。

原包同时存在普通物理与 SandFlow/Jobs/计算着色器路径。本轮并未逐行移植它的全部沙粒计算管线；采用批量绘制的思路优化当前可见方块玩法。相同算法也不能保证不同 Unity 版本和设备上的相同帧率。
